The one substantive issue is a design regression in ExpirationFilter.Dte: it now stores a pre-formatted wire string instead of structured data, which is inconsistent with every sibling variant in the same file (OnDate, Between, MonthYear all keep structured LocalDate/int fields) and with StrikeFilter's explicit rationale in the same package for avoiding raw-string passthrough in sealed filter types.

- [major] src/main/java/com/marketdata/sdk/options/ExpirationFilter.java:116 — Dte was changed from `record Dte(int days)` to `record Dte(String wireValue)`, pre-formatting the range/list into a wire string at construction time instead of storing structured data (e.g. min/max ints or a List<Integer>). This is inconsistent with every other variant in this same file — OnDate, Between, and MonthYear all keep structured fields (LocalDate/int) and let OptionsResource's applyExpirationFilter format them for the wire — and it directly contradicts the rationale given for the sibling StrikeFilter type in the same package ('prevents typos ... that a raw-string passthrough would silently ship to the server'). A consumer pattern-matching on ExpirationFilter.Dte now gets an opaque formatted string instead of the min/max or list of days it built the filter from, losing the type-safety and introspectability the sealed-interface design is meant to provide. Prefer storing structured data (e.g. separate Dte(int)/DteRange(int,int)/DteList(List<Integer>) variants or fields on Dte) and moving string formatting into OptionsResource alongside the other query-value formatting (e.g. strikeFilterWireValue).

- [minor] src/main/java/com/marketdata/sdk/options/ExpirationFilter.java:112 — The `Dte` record's canonical constructor (`record Dte(String wireValue) implements ExpirationFilter {}`) is implicitly public (nested types of a public sealed interface are public/static by default) and has no compact constructor validation, unlike `OnDate` which null-checks its argument. This means the non-negative / range / list-format validation performed by the `dte()`, `dteRange()`, and `dteList()` factory methods can be bypassed entirely by calling `new ExpirationFilter.Dte(anyString)` directly, despite the field's javadoc claiming the value is 'pre-validated'. Still, it's a correctness/encapsulation gap worth tightening (e.g. a compact constructor validating the wire format, or making the record's canonical constructor package-private) so the 'pre-validated' invariant documented in the Javadoc is actually enforced rather than merely conventional.
