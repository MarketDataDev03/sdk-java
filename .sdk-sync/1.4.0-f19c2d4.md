> This is a narrowly-scoped change (options chain `dte` filter widened from int to string form) with no new dependencies, no credential handling, no logging changes, and consistent, non-weakened test coverage matching the committed test plan. The only notable issue is a pre-existing (and slightly worsened) design gap: the `ExpirationFilter.Dte` record's canonical constructor is unavoidably public because it's nested in a public interface, so consumers can bypass the new range/list/non-negative validation by constructing `Dte` directly with an arbitrary string; actual injection risk is mitigated by the transport's existing URL-encoding of query values, so this is reported as a minor hardening item rather than a blocker.

- [minor] src/main/java/com/marketdata/sdk/options/ExpirationFilter.java:118 — The `Dte` record is nested inside the public sealed interface `ExpirationFilter`, so per JLS its canonical constructor is implicitly public and cannot be made more restrictive. Any consumer can therefore call `new ExpirationFilter.Dte(someArbitraryString)` directly, completely bypassing the `requireNonNegativeDte`/range/list validation done in the `dte()`, `dteRange()`, and `dteList()` factory methods, and have that raw string sent as the `?dte=` query value. This pattern already existed pre-change for the `int`-typed `Dte(int days)` constructor (which could already be bypassed with a negative int), but widening the field to `String` enlarges the bypass surface from 'any int' to 'any string', including empty strings, control characters, or overlong values reaching the wire unchecked. Downstream URL-encoding (per RequestSpec's documented contract) likely prevents this from becoming a request-splitting/query-injection vector, but it defeats the compiler-enforced validation invariant the sealed-type design is meant to guarantee. Consider validating `wireValue` in a compact constructor on `Dte` (format/charset check) so even direct construction can't produce an unvalidated value.
